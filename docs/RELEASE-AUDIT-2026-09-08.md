This audit covers the current working tree, including extensive changes already present before the audit. It is not a certification of a tagged release or the shared-drive download. No production relay settings, employee installations, releases, or cloud resources were changed.

**Release blockers and priority repairs**

| Priority | Finding and evidence | Required outcome |
|---|---|---|
| P0 | `install.ps1` downloads GitHub's latest release and executes it without asking the relay for its endorsement or checking its package hash. It fetches its own bootstrap from mutable `main`. | Route installation and updates through one trusted approval mechanism. Authenticate/check the downloaded artifact before executing its installer. Do not describe the pasted command as equivalent to the approved in-app updater. |
| P0 | `updater.py` previously followed GitHub when the relay was unavailable or unsigned-in, and rejected endorsed older versions. | **Partly fixed in this audit:** managed in-app updates now retain the installed version without valid approval, validate the approval fields, and allow an approved older version. Bootstrap and manual-menu issues remain below. Already installed clients do not gain these fixes until updated. |
| P0 | `packaging/Install.ps1` deletes the existing Python directory before copying the replacement. `Updater._swap()` has no transactional exception recovery around renames/copies, and removes previous backups before starting. | Stage and prove a full candidate before switching. Preserve a known-good install through disk-full, access-denied, antivirus locks, copy failure, and interrupted execution. Add startup recovery for a partially completed swap. |
| P0 | Tray and daily watcher instantiate separate updaters against the same directories. Repeated menu clicks start additional update threads. The tray uses public GitHub version checks before the approved update and restarts immediately, including during dictation. | One installation-wide update lock, one release-selection path, and one restart gate covering recording, transcription, and paste. Test simultaneous checks and endorsed rollback via the actual menu. |
| P0 | CI only packages the PyInstaller/Inno variant, while ADMIN recommends the Python ZIP. Bundle creation installs unpinned dependencies using the builder's interpreter into a hardcoded AMD64 Python 3.12.10 runtime, without verifying their interpreter/architecture match or running the resulting bundle. | Build and smoke-test the employee artifact in CI with a dummy endpoint and no production credentials. Pin the runtime, builder, and dependencies with hashes; verify Python/Tk/wheel compatibility; archive checksums and dependency inventory. Build a separately configured release artifact through the same process. |
| P0 | ADMIN says the Python bundle bypasses Smart App Control because everything executable is signed. The builder checks `python.exe` and four Tk binaries, then installs third-party native libraries without checking their signatures. | Test every shipped executable/DLL/PYD under actual company policies. Establish signing and IT allow rules where required. Do not promise that a signed interpreter guarantees the bundle is permitted. |
| P1 | Transcription client creation has no explicit application timeout/retry policy; cancellation only handles recording. Long recordings fall back to WAV if Opus encoding fails. | Add bounded network timeouts and a clear retry/cancel workflow that cannot paste a late result after cancellation. Enforce an encoded request-size limit or chunk long recordings. |
| P1 | `Config.save()` writes directly to the live file; `Config.load()` propagates invalid JSON/type errors. Refresh-token persistence also writes directly. | Use atomic replacement and retained recovery copies; validate settings and show actionable repair errors without discarding credentials. Test interruption, malformed JSON, and invalid settings types. |
| P1 | The authenticated relay forwards caller-controlled provider payloads/models. No per-user rate limit, allowed-model policy, or spend cap is evident in the reviewed implementation. Budget notifications are not caps. | Bound request size, allowed models, output budgets and per-user usage. Test expected peak concurrency against Lambda and provider limits. Verify deployed alarms, log retention, and cost controls; they were not inspected live. |

A five-minute recording at the default 16,000 samples/second × 2 bytes/sample is about **9.6 MB before multipart/base64 overhead**. That cannot fit Lambda's **6 MB synchronous invocation payload limit**, so the documented WAV fallback cannot guarantee recovery for long dictations. This is a calculation from the source defaults and [AWS's published quotas](https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.html), not a live load-test result.

Microsoft documents that application control can restrict PowerShell to Constrained Language or block unapproved scripts; an execution-policy bypass is not a general application-control exception. Smart App Control evaluates app binaries, so a signed Python launcher alone does not establish compatibility for its native dependencies. See [PowerShell application control](https://learn.microsoft.com/en-us/powershell/scripting/security/app-control/how-to-use-app-control?view=powershell-7.5) and [Smart App Control](https://learn.microsoft.com/en-us/windows/apps/develop/smart-app-control/overview).

**Make installation and everyday use simpler**

Prefer an IT-managed, signed installer distributed through the organization's existing software portal. If Intune is available, package it as a Win32 app with version detection, silent installation, upgrade and uninstall commands, and a clearly chosen per-user or machine installation context. The current installer assumes an interactive user profile and must not simply be run as SYSTEM. Microsoft supports these deployment controls through [Intune Win32 app management](https://learn.microsoft.com/en-us/intune/app-management/deployment/add-win32).

For unmanaged machines, provide one stable internal download page with one clearly named installer, its version, publisher, supported Windows versions, and a short setup walkthrough. Use normal Windows installation and uninstall registration. Preserve settings by default on uninstall, with an explicit option to remove credentials and settings. The current ZIP installer creates Desktop and Startup shortcuts but no Start-menu shortcut, even though recovery messages tell people to use Start.

First run should confirm work-account sign-in, microphone permissions, an input-level test, a usable dictation key, and a test dictation into a scratch text box. Many compact laptop keyboards do not expose Insert conveniently. Offer key selection during onboarding, and make the tray tooltip reflect toggle mode rather than saying “hold”. Provide an obvious microphone pause control and startup preference instead of requiring JSON edits.

Existing strengths include microphone-open deadlines, a dead-stream watchdog with backoff, microphone selection, language and translation controls, a status overlay, clipboard-change detection, a foreground-window guard, paste-last recovery, DPAPI protection of Google refresh tokens, and rotating local logs. Retain these while testing their real Windows behavior.

Remaining everyday-use concerns include following the Windows default microphone after docking/headset changes, clipboard image/rich-text preservation, clipboard history/cloud synchronization, focus changes inside the same application window, elevated applications, remote desktops, and accessibility. The foreground guard tracks a window, not the exact document field. Do not claim every text box or a success beep proves the target accepted the paste.

**Keep it functional over time**

Assign an IT installation owner and a service owner with a backup. Preserve the previous signed bundle and matching source/dependency manifest. Run an internal pilot across all hardware/policy combinations before staged expansion; a practical starting point is 5–10 representative users for five working days, followed by department-sized waves. Pause expansion on lost text, startup failure, authorization failure, or broken rollback.

Before each release, run automated tests, scan dependencies and bundled native binaries, verify the exact installer in a clean Windows profile, and exercise upgrade plus rollback. Introduce scheduled monitoring only after owners agree on cadence: daily synthetic transcription/cleanup with non-sensitive fixtures, actionable error/latency alarms, weekly operational review, and monthly runtime/dependency/model lifecycle review. These are recommendations; no recurring jobs were created by this audit.

`claude-haiku-4-5` is the current cleanup default; Anthropic's checked lifecycle table lists Haiku 4.5 as active. Continue monitoring rather than assuming the alias is permanent, and test older stored model settings during migration. See [Anthropic's deprecation policy](https://platform.claude.com/docs/en/about-claude/model-deprecations). Verify transcription model availability and both providers' actual organization quotas with an approved live smoke test before launch.

Revise the user documentation before rollout. The README still promises streaming-era network recovery even though transcription is now batch-based; it describes interim raw text that no longer matches the pipeline; and “nothing saved on your computer” omits diagnostic logs and possible clipboard history. Provider training/retention claims require confirmation against the organization's actual contracts and settings. Explain the continuously open microphone and pre-roll clearly. Replace hardcoded “message Tommy” ownership with a durable support contact and a redacted diagnostic export that excludes tokens, provider errors containing sensitive content, and dictation text.

**Changes made in this audit**

Only the in-app endorsement checks and approved-downgrade behavior were repaired, with eight additional regression cases and an updated existing fallback test. ADMIN now describes the changed failure behavior and explicitly notes the unresolved bootstrap bypass. The complete suite passes: **426 tests**. No installer was built, signed, distributed or endorsed. The audit remains a hold recommendation until the outstanding release blockers and Windows acceptance tests are completed.
